# Changelog

[简体中文](CHANGELOG.md) · English

All notable changes to **Transfer Any File** are documented here. The format follows
[Keep a Changelog 1.1.0](https://keepachangelog.com/en/1.1.0/) and the version in `package.json`
is the extension's manifest version, so a git tag `vX.Y.Z`, the built bundle and the store package
always name the same release.

## [Unreleased]

### Added

- **Image output parameters.** When the target is PNG, JPEG or WebP, the workbench gains an output
  tuning row: longest edge (800–4096 px; the accepted domain is 16–8192 px) is always offered,
  quality (40–90%) and target size (20–2000 KB; accepted 1 KB–50 MB) appear for JPEG and WebP only
  (PNG has no quality dial), and render density (96/144/200/300 DPI) appears only when the batch
  contains a PDF, because DPI affects nothing else. All of them are applied in one funnel
  (`encodeCanvas()` in `utils/core/image-utils.ts`), so the four routes that can produce
  an image — image→image, SVG→image, HTML→image, PDF→image — cannot disagree about what "quality 70%"
  means. A target-size request walks the quality ladder before it starts discarding pixels, and is a
  ceiling chased rather than guaranteed: the smallest reachable result is returned instead of an error.
  Parameters persist under `fat:outputOptions`, apply to image targets only, and a parameter set left
  over from an earlier image batch cannot degrade a later document conversion.
- **Conversion presets.** The current target plus its output parameters save as a named card (up to
  12, names clamped to 40 characters, untitled saves describe themselves) above the format picker. A
  preset is bound to a target, not to a source format — "PNG → 200 KB WebP" applies whether the next
  drop is Markdown, PDF or PNG. Applying one before any file is loaded is remembered and applied to
  the next upload; if the batch that arrives cannot reach the preset's target, that is said out loud
  instead of the click doing nothing. Stored under `fat:presets` and sanitised on read, so stale or
  hand-edited storage cannot put an out-of-range parameter on the dial.
- **`pnpm verify:listing`** — measures every field pasted into the Chrome Web Store dashboard against
  its real limit and fails if the listing sheet drifts from `public/_locales/*/messages.json`,
  `wxt.config.ts` (its `default_locale` and `__MSG_` placeholders), `package.json` or
  `.github/repo-metadata.json`. Runs in CI and in the release workflow. The store truncates
  over-length fields silently instead of rejecting them, so a field that grows three characters used
  to be able to reach production as a cut-off sentence.
- **`CHROMEWEBSTORE.md → 提交速查` (submission worksheet)** — the dashboard's four tabs in fill order, with each
  short field verbatim and the long copy referenced by section.
- **The big-batch confirmation can dismiss itself.** That dialog now carries a **Don't ask again** box,
  which writes the same `fat:confirmConvert` preference the Preferences switch owns — the question is
  answered where it is asked, and the menu stays the way to bring it back. Checking the box and then
  cancelling persists nothing: the preference is only written once the batch is confirmed.
- **A seventh store listing frame.** `screen-07-presets` puts the output parameters and the preset chips
  on one real screen — a PDF staged with a WebP target, arrived at by clicking a chip rather than the
  dropdown — generated by `pnpm assets:capture` alongside the other six. The listing sheet now picks
  five of seven.
- **A pipeline diagram and a contact section on the product page.** `#how` lays the six internal steps of
  one conversion — detect, intersect, screen out, route, convert, deliver — out as a flow whose connectors point
  at the node that actually follows them, so the 27 greyed-out combinations and the BFS chain
  (`MD → HTML → PDF`) are shown rather than asserted. `#contact` publishes the channels that reach the author
  behind `docs/assets/wx-qrcode/wechat-qrcode.jpg` (WeChat `lld_1025`, note `taf`), the listing email and the
  issue tracker, and says in the copy that this is a personal-add code rather than a group code that expires.
  The page's `dateModified`, its visible "last updated" line and the `sitemap.xml` entry move to 2026-09-15.
  Nothing here enters the bundle — `docs/` is repository documentation and `pnpm build` is checked to exclude it.
- **A WeChat group call-out in the Chinese promo draft.** `docs/promo/wechat-article.md` closes with the QR code
  and the `taf` friend-request note, framed as the place to ask for a missing format. The English draft keeps the
  issue tracker as its only channel: a WeChat group is not a plausible route to an English reader, and the two
  drafts stay in step on numbers and evidence, not on distribution channels.

### Changed

- **Bilingual root documents standardised on "Chinese primary + `.en.md` English twin".**
  `CONTRIBUTING`, `SECURITY` and `CHANGELOG` previously held English in the primary filename and Chinese in
  `*.zh-CN.md`, while the README pair ran the other way — three bilingual conventions in one repository, the third
  being Chinese/English side by side inside the PR and issue templates. The README is no longer the exception: the
  Chinese text takes the primary filename, English moves to `.en.md`, the switch line under each H1 flips, and every
  reference site migrates with it (both READMEs, `AGENTS.md`, `.qoder/rules/wxt-rules.md` §10, `docs/llms.txt`, the
  PR template, `release.yml`). `git mv` was used, so the history of each file survives the rename.
  **Side effect**: GitHub Release bodies are now taken from the Chinese `CHANGELOG.md` — the `release.yml` awk only
  matches the `## [X.Y.Z]` heading, which is identical in both files, so no script change was needed, while the
  trailing cross-language pointer flips from "中文更新日志见…" to "英文更新日志见 `CHANGELOG.en.md`…".
  Historical entries keep the `*.zh-CN.md` filenames they used at the time; they are records, not references.
- **`CHROMEWEBSTORE.md` is now written in Chinese, ordered the way the dashboard is filled.** The 899-line
  English file mixed four kinds of content: a to-do list, the copy to paste, asset specifications and policy
  forensics. The body now runs 提交速查 → 商店文案 → 图形与素材 → 权限与隐私申报 → 分发与开发者信息 →
  首次上架（手工步骤）→ 上架后的运营 → 审核要点 → 版本历史, with both rejection notices and their before/after
  tables moved to the end — they are evidence, not something to re-read on every submission.
  **The 12 paste blocks are unchanged to the byte** (re-extracted from both files by their field labels and
  compared). Translating it without losing the guard required rewriting `verify:listing`'s literal anchors in the
  same change: leave the field markers and the `## 提交速查` / `## 商店文案` boundaries untranslated and the script
  throws `heading not found`, turning CI red. The line count did not fall (899 → 911), because CJK costs three
  bytes a character and the paste blocks plus evidence tables are the floor; what roughly halved is the prose
  outside fences — 71,800 → 42,254 characters. **It was not split into several files**: the paste copy, its length
  assertions and its anchors have to live in one document, or "edit the field in one place" becomes "reconcile two".
- **GitHub repository metadata moved out of the store document into `.github/repo-metadata.md`.** Why the About
  description opens with `file format converter`, why `file-format-converter` and `file-converter` are both kept
  (one is a small topic whose listing tops out at 340 stars, the other is head-dominated by an 18.8k-star project),
  the reasoning behind spending the full 20-topic budget, and the one-off `curl` for a machine without `gh` — none
  of that is material you paste into the store dashboard. The dead references to the old section name in
  `.github/repo-metadata.json` and `repo-meta.yml` now point at the new file.
- **The `.github` operational documents are Chinese-primary.** Comments, `::error::` messages and step summaries
  across all four workflows (ci / static / release / repo-meta) are now Chinese; **workflow and step names stay
  English**, because they are the stable identifiers in the Actions UI and in status badges, and renaming them
  makes history look like a different job. Both issue templates lead with the Chinese name, and the English-only
  placeholders and the pre-filled environment block are now Chinese, with button labels taken from the real
  `utils/i18n/zh.ts` values (`开始转换`).
- **A first run opens in the browser's language.** The default was Chinese for everyone, so an
  English browser showed a workbench in Chinese until the switch was found. `navigator.languages` is
  now the fallback whenever no explicit choice is stored — the only signal an offline extension has —
  and a stored `zh`/`en` still wins. Because the preference is written only when it is changed, an
  existing profile that never touched the switch has no stored value: it moves to its browser's
  language on the next open, and switching back is one click that now persists. `<html lang>` matches
  the rendered language and follows every later switch, instead of being absent from the document.
- **The target picker is type-to-filter.** With 14 formats on the list, typing `web` or `xsl` now
  narrows it, and a query that matches nothing says so instead of showing an empty box.
- **Privacy-disclosure guidance corrected.** The store asset pack previously said to declare "we don't
  collect any user data". That form asks about _handling_, and Google requires disclosure for data
  processed or stored only on the device — so the answer for this extension is an affirmative
  declaration of on-device file processing. The previous wording was the largest submission risk in
  the document. `docs/privacy.html` now states the collect/handle distinction in both languages.
- **The listing's default language is now Chinese, and the package is what decides it.** The dashboard's
  default language is a read-out of the package rather than a setting: the store opens a listing page per
  `_locales/<code>/` directory that actually ships, and the default one is the manifest's `default_locale`.
  This project had neither, so the item had a single English page and the Chinese copy had nowhere to be
  pasted. The package now carries `public/_locales/zh_CN/` (`default_locale`) and `public/_locales/en/`, each
  holding just `extensionName` and `extensionDescription`, while `wxt.config.ts` turns its name and
  description into the `__MSG_extensionName__` / `__MSG_extensionDescription__` placeholders. **They have to
  live under `public/`**: `default_locale` resolves against the extension root, and WXT only moves
  `publicDir` verbatim into `.output/chrome-mv3` — this is the one place `public/` should hold source.
  Two things change: the name Chrome displays, with its permission and error strings, resolves per browser UI
  language (English systems still read English — nothing is taken from them), and the listing defaults to
  `Chinese (China)` with English demoted to an additional localization. **The in-app language is
  untouched** — that stays `useI18n` and `fat:locale`, a separate layer from the listing's. The guards move
  to the same shape: `verify:listing` now checks that both locale files carry an identical key set and that
  every value equals its paste block to the byte, and `verify:meta` compares `package.json#description`
  against `_locales/en`'s `extensionDescription` instead of a `wxt.config.ts` literal. **The cost, recorded
  on purpose**: the Chinese short description has never once been through review and it is now the field
  being reviewed, so a future verdict cannot be attributed to the copy or to this switch alone.
- **The README pair flipped: `README.md` is now Chinese, `README.en.md` English.** GitHub renders
  `README.md` on the repository home page and nothing else, and the primary audience reads Chinese — so the
  front page was showing the secondary language to most visitors. Every reference site moves with it: the
  language-switch line and nav anchors in both READMEs,
  `AGENTS.md`, `CONTRIBUTING.md` / `CONTRIBUTING.zh-CN.md`, the PR template, `CHROMEWEBSTORE.md`'s file list,
  `docs/llms.txt`, the product page footer and the capture script's comment. `.qoder/rules/wxt-rules.md` §10
  recorded this as the single exception to the `*.zh-CN.md` naming rule — later the same day the whole repository moved
  in this direction, which is the first entry of this section.
- **Product page structured data and headings** — the `<h1>` names the product category, JSON-LD gains
  `keywords`, `datePublished`, `WebSite` and `SoftwareSourceCode` nodes, the network claim in the FAQ
  is scoped to first-party source (the version a reviewer can actually check), the three citable
  sections that had no inbound link are now reachable from the footer, and an install duration that
  contradicted its own markup is gone.
- **Product page and `llms.txt` metadata** — both meta descriptions were 284 and 225 half-width
  characters against a snippet window of about 155, so the differentiator (`no uploads, no account,
zero network requests`) and the Chinese equivalent never appeared in a search result, and the
  English one broke off mid-word. They now lead with the search phrase and the format count and close
  inside the window; the format enumeration they gave up is already in the body, the FAQ schema and
  the JSON-LD. `llms.txt` quoted a 3.71 MB bundle where `pnpm build` reports 3.73 MB.
- **README** — a screenshot caption that claimed forty files over a three-file capture, and two
  numbers about third-party services and conversion speed that the repository cannot evidence.
- **Manifest description and repository housekeeping.** The manifest and package description now name
  the three format categories instead of enumerating eight formats: the 2026-09-14 store review rejected
  the draft over keyword stuffing in exactly this field, and the four places that mirror it
  (`CHROMEWEBSTORE.md`'s Short Description, `package.json#description`, `wxt.config.ts`, the promo
  image) must stay in step.
  `scripts/check-package-meta.mjs` now reads the description quote-agnostically, so a Prettier pass that
  rewrites `wxt.config.ts` to single quotes no longer breaks the check. The icon A/B scratch directory
  (`.icon-compare/`) and the two throwaway scripts that produced it (`scripts/tmp-icon-compare.mjs`,
  `scripts/visual-history.mjs`) are deleted.
- **Store listing copy, second de-enumeration.** The 2026-09-15 review rejected the draft again on the same
  policy line, this time quoting the three family bullets of the detailed description's WHAT YOU CAN CONVERT.
  Both detailed descriptions now state coverage by family and count instead of by name — format-name tokens
  went from 94 to 3 in English and 96 to 3 in Chinese, and the surviving three are the two PDF limitations
  that cannot be phrased without naming PDF plus the history export's container. The COMMON CONVERSIONS /
  常用转换 pair list is deleted outright, and `screen-02-batch`'s burned-in caption lost its three format
  names, so every listing frame and promo tile was recaptured. Nothing about the shipped extension changed;
  the per-format matrix the listing no longer carries stays published on the product page.
- **Licence switched from ISC to MIT.** The permissions are the same — permissive, no copyleft, no patent grant either
  way — but MIT is the SPDX identifier reviewers, aggregators and dependency tooling recognise without a lookup, and
  it is what this repository now advertises. Updated in lockstep: `LICENSE`, `package.json#license`, both READMEs
  (badge, comparison row, FAQ, License section), both CONTRIBUTING files, the `CHROMEWEBSTORE.md` Q&A pair,
  `docs/llms.txt`, both promo drafts, and the product page's two JSON-LD `license` nodes plus its four visible
  mentions. Nothing in the shipped extension reads a licence string, so behaviour, storage and permissions are
  untouched.

### Fixed

- **A cancelled batch no longer reported as a completed one.** Cancelling mid-batch left the
  "conversion finished" alert over the partial results, and cancelling before the first file
  finished left the screen empty, as though the button had done nothing. A stopped batch now reads
  as stopped, with the counts of what is still usable, and is announced that way to a screen reader.
- **Cancel gave no acknowledgement.** A long step (a big PDF, a tall HTML page) keeps running for a
  moment after 取消转换 / Cancel is clicked, and the button carried on counting during that window, so
  people clicked it again. The button now reads "cancelling…" and disables itself until the batch ends.
- **A stray reload could discard a batch in silence.** Uploaded files live only in memory, so closing
  or reloading the tab mid-conversion lost the batch with no warning; the browser now asks first.
- **Greyed-out combinations could still run.** `utils/core/conversion-policy.ts` was consulted only by
  the format picker, so any caller that set a target without going through the dropdown — a stale
  selection, a reused history pair — could start a conversion that always fails or emits a placeholder.
  The check now sits in `ConverterRegistry.resolvePath()`, the one place a path is resolved.
- **Two batches on the same day overwrote each other's archive.** The ZIP name carried a
  date-only stamp (`converted-2026-09-14.zip`); it now uses the same second precision as per-file
  names.
- **A failure's cause was thrown away.** Converters translate an error into a classified key for the
  headline, which dropped what pdf.js / jsPDF / the canvas actually complained about. The raw message
  is now carried as `Error.cause` and shown in the expanded diagnostic.
- **Large HTML→PDF and PDF→image runs could exhaust the tab.** A tall document rasterized at 2×
  pixelRatio is roughly 1.3 GB of canvas buffer, and the buffer survives as long as the element does
  — losing the reference is not enough while the converter still holds it. PDF→image releases each
  page's canvas as soon as its bytes are encoded; HTML→PDF keeps its source canvas and its one slice
  canvas alive for the pagination loop and releases both when the loop ends. Either way the pixel
  buffers no longer outlive the conversion.
- **PNG→PDF had no size guard.** `image-to-pdf.ts` clamped oversized inputs and rejected 0×0 images;
  `png-to-pdf.ts` did neither, so a very large PNG produced an unrenderable PDF and a 0×0 one produced
  an empty page. PNG→PDF now keeps its lossless byte-for-byte embed and downscales only past the
  canvas limit, and it measures the picture (`naturalWidth`) rather than a CSS-adjusted box.
- **A JPEG fed to PDF through a chain was embedded as a PNG.** `image-to-pdf.ts` chose its embed format
  from `input.type`, which is sniffed from the uploaded file and is empty on an intermediate blob — so a
  multi-step route that produced a JPEG stored the lossless PNG of it and inflated the PDF. The choice
  now reads `from`, the format the converter is registered under.
- **An invisible target size silently shrank PNG output.** Target size is offered for JPEG / WebP only,
  but its value persists in `fat:outputOptions` across target changes: retarget a batch to PNG and that
  20 KB ceiling still travelled with the encoder. `encodeCanvas` gated its quality ladder on lossy
  containers but not the pixel-discarding one, so a PNG was downscaled as far as 40% to chase a number
  the panel neither shows nor lets you clear. Target size is now lossy-only, like quality, and a PNG
  comes back byte-identical to one converted with no parameters at all.
- **Non-UTF-8 CSV/HTML could decode to mojibake or fail.** The fallback chain was UTF-8 → GBK; it is
  now UTF-8 → GB18030 → GBK, which covers the characters GBK cannot represent while still resolving a
  lone `0x80` the way legacy Windows tooling writes it. The chain now also reaches markup, so a GBK
  page rasterizes as itself instead of as a picture of mojibake. The two input classes keep different
  failure policies: markup (HTML, SVG) falls back to a lossy UTF-8 decode when no encoding in the
  chain covers the bytes — the tolerant behaviour it always had — while CSV and JSON still report a
  decode failure, because there output no reader could open is worse than an error the user can act on.
- **White text on the primary button was hardcoded.** `#fff` is illegible on the light green and
  orange themes; the foreground now comes from `--fat-on-primary`, so a theme chooses its own label
  colour instead of inheriting one that does not contrast.
- **…and the label still failed AA in 7 of the 12 theme × mode combinations.** Measured off the live
  button, every one of those failures sat in the hover or active shade — the resting fill already
  cleared 4.5:1 in all 12, 4.70:1 at worst — because the two interaction states followed the theme's
  lightness ladder instead of the label. They are now derived from the resting fill in the direction
  away from the label (`--fat-btn-solid*` in `assets/theme/tokens.css`), and a dark-mode button takes
  the page ink rather than white, which also lifts those fills to 6.15–9.73:1 against the card behind
  them (WCAG 1.4.11). Worst label today: 4.70:1. The suite asserts the label in rest, hover and
  pressed states for all 12 combinations. What is left is documented rather than fixed: the fill of
  the light forest-green and orange buttons stays under 3:1 against a card (2.21 / 2.96:1 at their
  lightest state), because those fills are close to white and deepening them would spend the label's
  margin.
- **A mixed-format batch displayed one file's route.** The path strip under the picker described
  `sourceFormats[0]` as if it covered the batch; each file resolves its own chain, so the strip is
  hidden for a mixed batch.
- **The upload zone lit up for a drop it would refuse** while intake was disabled.
- **The e2e harness had no working `chrome.storage`.** `page.addInitScript()` was handed a bare arrow
  function, which Playwright evaluates as an expression and never calls — so every assertion about a
  persisted preference ran against a page with no storage, and the pinned-locale guard the suite
  depends on had never applied. The stub is now an IIFE; the suite passes with storage actually
  functioning.

## [1.0.0] - 2026-09-07

First release: an offline file format converter for Chrome (Manifest V3). Every conversion runs in
a tab on your own machine — no server, no account, no network request.

### Added

- **Workbench** — clicking the toolbar icon opens the converter in a new tab. There is no popup and
  no side panel; the whole job happens on that one page. Dropping files works anywhere on that page,
  not just on the upload zone, with a full-page overlay confirming the drop target.
- **14 formats** — documents (Markdown, HTML, Word `.docx`, PDF, TXT), data (CSV, Excel `.xlsx`,
  JSON) and images (PNG, JPEG, WebP, BMP, GIF, SVG); 46 registered direct routes, and BFS over the
  converter registry makes 143 source→target combinations reachable, of which the format picker
  offers 116 — the other 27 are greyed out with a reason by `utils/core/conversion-policy.ts`
  (image→text/data needs OCR, PDF→data has no table structure to read).
- **Automatic multi-step chains** — `Markdown → PDF` runs as `Markdown → HTML → PDF`, and the route
  is shown under the picker. Adding a converter instantly unlocks every route through it.
- **Mixed-format batches** — files of different types share one target; only formats reachable from
  _every_ selected file are offered. One unreadable file never blocks the batch: failures are listed
  per file with their reason, and each one expands to show the route it tried, the step that broke,
  and a copyable plain-text diagnostic for filing an issue.
- **Control** — cancel a long batch with finished results kept, undo the previous batch, confirm
  before a batch larger than 5 files or 20 MB, optional desktop notification when a job finishes in
  a background tab, rebindable `Ctrl/⌘ + Enter` to start a conversion.
- **Preview and edit** — source and result side by side with a draggable divider, synchronised
  scrolling and source-only / result-only modes; `1` / `2` / `3` switch those modes and `←` / `→`
  nudge the divider. Text results (Markdown, HTML, TXT, JSON, CSV) are editable inline before
  download, and any text result can be copied to the clipboard. The divider position and the history
  card's collapsed state persist across sessions.
- **Recent targets** — the last 6 target formats you used are grouped at the top of the picker as
  _Recently used_, filtered to the ones still selectable for the current batch.
- **Batch I/O** — ZIP download with a per-entry strategy (text deflated to roughly a tenth,
  already-compressed outputs stored as-is), ZIP intake (drop an archive and its supported files join
  the batch), one CSV per worksheet for multi-sheet workbooks, one image per page for multi-page
  PDFs, and paste-from-clipboard (`⌘V` / `Ctrl+V`).
- **Chinese spreadsheets stay readable** — CSV reads UTF-8 with automatic GBK fallback and writes
  UTF-8 with a BOM, so exports from domestic Chinese software open without mojibake.
- **History** — the last 50 conversions as metadata only (names, formats, sizes, never contents):
  search by file name, filter by source or target, reuse a combination in one click, per-record
  delete, a size-trend sparkline, and JSON export / import merged by record ID.
- **Personalisation** — 6 accent colours × light / dark / follow-system, applied before mount so
  there is no flash of the wrong palette; Chinese and English interface (default Chinese).
- **Accessibility** — skip link to the main content, visible focus rings, ARIA labelling and
  `prefers-reduced-motion` fallbacks; the end-to-end suite reads two contrast pairs back off the live page in all 6
  themes × light/dark (brand text on the topbar at 4.5:1, focus ring on a card at 3:1) and asserts them per theme.
- **Privacy by structure** — the manifest requests only `storage`, declares no `host_permissions`
  and ships no remote code; `pnpm verify:offline` asserts on every CI run that no first-party source
  file issues a request.
- **Tooling** — WXT + Vue 3 + TypeScript + Element Plus (on-demand), heavy conversion libraries
  dynamically imported per converter so the first paint stays small; a Playwright suite that drives
  the built bundle over `fixtures/`; CI with lint, build and end-to-end; GitHub Pages published from
  `docs/`; a release workflow that builds the store package and checks its contents.

### Known limits (documented rather than hidden)

- PDF output is rendered page by page as images, so its text is not selectable or searchable.
- PDF input extracts text only; layout and embedded images are not preserved.
- No OCR — image → TXT/CSV/Excel is greyed out with the reason shown, because an OCR model would add
  tens of megabytes and a download, which the offline guarantee rules out.
- BMP, GIF and SVG can be converted _from_ but not _to_: browsers expose no encoders for them (GIF
  uses its first frame, SVG is flattened before rasterising).
- Limits: 100 MB per file (warned above 20 MB), 200 files per batch. No video, audio, e-book or CAD
  formats.
